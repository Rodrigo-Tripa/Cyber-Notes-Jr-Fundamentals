# Browser and Endpoint Privacy

> Network anonymity can hide where traffic comes from, but it cannot guarantee that the device generating that traffic is itself indistinguishable.

## 1. The Endpoint as an Identity Surface

An anonymity architecture does not begin at the network. Before traffic reaches an anonymity network, information is generated by the endpoint: the physical device, operating system, applications and browser.

A simplified model is:

`User → Device → OS → Application → Browser → Network`

Every layer can expose characteristics that contribute to identification or correlation.

The endpoint may reveal information intentionally, such as an account username, or indirectly through configuration and behaviour. A browser may expose a particular combination of language, timezone, screen characteristics and sofware capabilities. An operating system may maintain persistent state. Applications may create their own network connections independently of the browser.

This creates an important distinction:

`Network anonymity → hides or obscures network origin`

`Endpoint privacy → minimises information exposed by the originating environment`

A strong anonymity architecture therefore has to consider both.

---

## 2. Browser Fingerprinting

A browser fingerprint is a collection of observable characteristics that can be combined to distinguish one browser environment from others.

Potential fingerprinting signals include:

- Browser and operating-system characteristics
    
- Screen dimensions
    
- Language and locale
    
- Timezone
    
- Installed fonts
    
- Graphics capabilities
    
- Canvas rendering
    
- WebGL characteristics
    
- Audio processing
    
- Supported APIs
    
- Hardware concurrency
    
- Device capabilities
    

Individually, many of these properties are not particularly identifying. The problem is their combination.

For example, a website might observe:

`Linux + unusual browser configuration + specific fonts + unusual display characteristics + specific graphics capabilities`

The resulting combination may be sufficiently uncommon to distinguish the environment from a large population.

This is why anti-fingerprinting systems often prefer **standardisation** over allowing every user to expose a unique configuration.

A strange configuration can become an identifier.

---

## 3. Entropy and Uniqueness

Fingerprinting can be understood as an information problem.

If a characteristic is shared by almost everyone, it provides little identifying information.

If a characteristic is extremely rare, it provides substantially more.

This can be expressed using information entropy:

`I(x) = -log₂ p(x)`

where `p(x)` is the probability of observing characteristic `x`.

A characteristic observed in half of all users contributes relatively little information. A characteristic observed in one user among thousands contributes substantially more.

Real browser fingerprints contain multiple characteristics, and their combined information can be much more useful than any individual signal.

However, fingerprint uniqueness is not necessarily the same as permanent identification. A fingerprint becomes particularly powerful when it can be observed repeatedly and linked across sessions.

This makes **stability** as important as uniqueness.

A highly unique fingerprint that changes constantly may be less useful for tracking than a moderately distinctive fingerprint that remains stable for months.

---

## 4. Anti-Fingerprinting and Standardisation

A common intuition is that privacy improves when a browser exposes less information by allowing users to customise everything.

The opposite can sometimes be true.

Suppose a privacy-conscious user modifies:

- User-Agent
    
- Fonts
    
- Screen configuration
    
- Browser APIs
    
- Rendering behaviour
    
- Language
    
- Timezone
    
- Extensions
    

The resulting configuration may become highly unusual.

Instead of joining a large anonymity set, the user may effectively create a smaller one:

`Normalised configuration → many similar users`

`Unique configuration → few similar users`

Privacy-oriented browsers therefore often attempt to **reduce distinguishability** rather than simply eliminate every possible signal.

This can involve standardising observable properties, restricting access to APIs, isolating state and limiting functionality that can be abused for fingerprinting.

The objective is not necessarily:

> "Expose absolutely nothing."

It is:

> **"Expose as little identifying information as possible while remaining difficult to distinguish from other users."**

---

## 5. Cookies, Storage and Persistent State

Fingerprinting is only one mechanism for tracking browsers.

Web applications can also maintain state through mechanisms such as:

- Cookies
    
- Local Storage
    
- Session Storage
    
- IndexedDB
    
- Cache-related state
    
- Service workers
    
- Authentication tokens
    

These mechanisms are useful for legitimate functionality such as authentication and preferences, but they can also establish persistent identifiers.

Consider an anonymous session that obtains an identifier:

`Browser → ID: X`

If the same identifier appears during a later session, the two sessions can potentially be linked:

`Session A → X ← Session B`

The observer may still not know the real-world identity of the user, but it now knows that both sessions probably belong to the same entity.

This is a **linkability problem**.

Privacy-oriented browser architectures therefore attempt to isolate or clear state between contexts, restrict third-party tracking and prevent identifiers from freely crossing between unrelated activities.

---

## 6. Network and Application Leaks

Routing browser traffic through an anonymity network does not automatically guarantee that every network interaction follows the same path.

Applications may generate their own connections. Browser features may interact with local networking infrastructure. Misconfiguration can cause traffic to bypass the intended anonymity layer.

Potential leak surfaces include:

- DNS resolution
    
- WebRTC
    
- Direct application connections
    
- Background services
    
- Browser extensions
    
- External protocol handlers
    
- System telemetry
    
- Automatic updates
    
- Synchronisation services
    

The underlying problem is architectural:

`Browser → Intended anonymity path`

may coexist with:

`Application → Direct Internet connection`

If the second path exposes identifying information, the anonymity architecture can be undermined regardless of how well the primary connection is protected.

For this reason, anonymity-oriented environments generally favour **strict control over network access and application behaviour**.

---

## 7. Operating System and Persistent Traces

The endpoint can also retain information locally.

Operating systems and applications commonly generate:

- Logs
    
- Caches
    
- Temporary files
    
- Browser profiles
    
- History
    
- Authentication state
    
- Shell history
    
- Application databases
    
- Crash reports
    
- Recently used file records
    
- Persistent configuration
    

These traces may not be visible to a remote website, but they become relevant when the threat model includes physical access, forensic acquisition or malware.

This introduces the concept of an **amnesic environment**: a system designed to minimise persistent traces between sessions.

An amnesic system does not magically erase every possible trace. Hardware, firmware, storage devices and external infrastructure may have their own persistence mechanisms.

Its purpose is to reduce the amount of information intentionally retained by the operating environment.

This distinction is important:

`No persistent user data`

does not necessarily mean:

`No possible forensic evidence`.

The security property depends on the exact implementation and threat model.

---

## 8. Endpoint Compartmentalization

One of the strongest strategies for limiting correlation is to separate activities into distinct environments.

Consider a single browser profile used for everything:

`Personal identity`  
`Anonymous research`  
`Professional activity`  
`Sensitive communications`

If identifiers, cookies, browser state or behavioural characteristics cross between these contexts, the activities can potentially become linked.

Compartmentalization instead creates boundaries:

`Identity A → Environment A`

`Identity B → Environment B`

The objective is to make accidental information flow between identities more difficult.

This can be implemented at different levels:

`Browser profile`

`Separate browser`

`Separate user account`

`Virtual machine`

`Separate operating system`

`Dedicated physical system`

The stronger the isolation requirement, the stronger the boundary generally needs to be.

However, compartmentalization is only effective if the user respects the boundary. Logging into the same identifying account from multiple compartments can immediately reconnect otherwise separate identities.

---

## Core Principle

> **An anonymous network cannot compensate for an identifiable endpoint.**

Browser fingerprinting, persistent state, application behaviour, network leaks and local traces can all create attribution or linkability paths outside the anonymity network itself.

Effective endpoint privacy therefore combines several principles:

`Minimise exposed information`

`Reduce distinguishability`

`Control persistent state`

`Prevent unintended network paths`

`Separate identities`

`Minimise local traces`

The goal is'nt to create a perfectly invisible computer. Such a system is unrealistic. The practical objective is to reduce the number and reliability of signals that allow an observer to distinguish, track or correlate the endpoint.

This makes browser and endpoint privacy a complementary layer to anonymity networks rather than a replacement for them.
